# 2D 스팀 게임 개발 툴체인 및 아키텍처 기획

## 1. 프로젝트 개요

### 목표
- 일러스트·손그림 기반의 2D 게임 개발
- 고정 화면 또는 스테이지 방식
- 중소규모 인디 게임
- 최종 목표: Steam 출시
- 개발 방식: 1인 개발을 기준으로 하되, 향후 협업과 콘텐츠 확장을 고려

### 최종 엔진 선정

**Godot 4.x + GDScript**

Love2D도 2D 게임 제작에 충분히 사용할 수 있지만, 이번 프로젝트에서는 Godot을 추천한다.

선정 이유:
- Scene 기반으로 스테이지와 화면을 독립적으로 구성할 수 있다.
- 이미지, 레이어, UI, 애니메이션을 에디터에서 편집할 수 있다.
- 화면 전환, 입력, 충돌, 저장 등 게임 제작에 필요한 기반 기능이 내장되어 있다.
- 코드 중심 개발과 에디터 중심 작업을 함께 사용할 수 있다.
- 무료 오픈소스이며 상업적 이용과 유료 판매가 가능하고 엔진 로열티가 없다.

## 2. 엔진 비교: Godot vs Love2D

| 비교 항목 | Godot | Love2D |
|---|---|---|
| 개발 방식 | 에디터 + 코드 | 코드 중심 |
| 주 언어 | GDScript / C# | Lua |
| 이미지 배치 | 에디터 지원 | 직접 구현 |
| 레이어 관리 | 내장 기능 | 직접 구현 |
| 화면 전환 | Scene 시스템 | 직접 구현 |
| UI 제작 | Control 노드 | 직접 구현 |
| 애니메이션 | AnimationPlayer 등 | 라이브러리 조합 |
| 스테이지 제작 | Scene 및 Resource | 별도 포맷 설계 |
| 해상도 대응 | 내장 설정 | 직접 구현 |
| 상업적 이용 | 가능 | 가능 |
| 로열티 | 없음 | 없음 |

### Godot을 선택하는 이유

이번 게임은 픽셀 아트가 아닌 일러스트 기반이며, 고정 화면과 스테이지 단위로 콘텐츠를 제작한다.

따라서 다음 작업의 반복 효율이 중요하다.

- 배경 및 오브젝트 이미지 배치
- 화면과 레이어 구성
- 스테이지 단위 제작 및 재사용
- 캐릭터 및 오브젝트 애니메이션
- UI와 화면 전환
- 해상도 및 입력 처리

Love2D에서도 구현할 수 있지만 맵 편집, UI, 애니메이션, 리소스 관리 도구를 직접 구성해야 한다. 게임을 완성하고 출시하는 데 집중하려면 Godot이 더 효율적이다.

| 프로그래밍 | GDScript | 게임 시스템 구현 | 무료 |

| 이미지 편집 | Krita / Affinity | 이미지 보정 및 합성 | 무료 플랜 또는 별도 조건 확인 |
| 애니메이션 | Godot AnimationPlayer | 오브젝트, UI, 간단한 캐릭터 애니메이션 | 무료 |
| 본 애니메이션 | Spine (선택) | 캐릭터 리깅 및 반복 모션 | Essential 약 $69부터 |
| 사운드 편집 | Audacity | 효과음 편집 | 무료 |
| 오디오 제작 | REAPER (선택) | BGM 및 사운드 믹싱 | 할인 라이선스 약 $60 |
| 코드 편집 | Godot Editor / VS Code | 코드 작성 및 디버깅 | 무료 |
| 버전 관리 | Git | 소스 및 프로젝트 버전 관리 | 무료 |
| 원격 저장소 | GitHub | 백업 및 협업 | 무료 플랜 |
| 배포 | Steamworks | 빌드, 상점, 업적 등 | 게임당 Steam Direct $100 |

비용은 USD 기준의 예산 참고값이다. 실제 구매 시점의 가격, 세금, 환율 및 라이선스 조건을 확인해야 한다.

### 3.1 Godot

- 공식 사이트: https://godotengine.org/
- 라이선스: MIT
- 비용: 무료
- 상업적 게임 제작 및 판매 가능
- 엔진 로열티 없음
- 배포 시 Godot 저작권 및 라이선스 고지를 포함한다.

### 3.2 Krita

- 공식 사이트: https://krita.org/
- 라이선스: GPL-3.0
- 비용: 무료
- 배경, 캐릭터, 오브젝트, UI 원화 제작에 사용한다.
- Krita로 제작한 이미지 결과물은 상업용 게임에 사용할 수 있다. Krita 프로그램 자체의 소스코드 라이선스와 제작 이미지의 권리는 구분한다.

### 3.3 AnimationPlayer

- Godot 내장 기능
- 비용: 무료
- 활용 대상:
  - 오브젝트 이동 및 회전
  - 문 열림, 서랍 열림
  - 조명 및 투명도 변화
  - UI 전환 및 버튼 효과
  - 간단한 캐릭터 모션

처음부터 Spine을 구매하지 말고 Godot 내장 애니메이션으로 프로토타입을 제작한다. 본 애니메이션이 반복적으로 필요해질 때 Spine 도입을 검토한다.

### 3.4 Audacity 및 REAPER

- Audacity: https://www.audacityteam.org/
- REAPER: https://www.reaper.fm/

Audacity는 효과음 자르기, 노이즈 제거, 음량 조정 등에 사용한다. REAPER는 BGM 제작과 여러 사운드 트랙의 믹싱이 필요할 때 선택적으로 구매한다.

### 3.5 Git 및 GitHub

- Git: https://git-scm.com/
- GitHub: https://github.com/

게임 프로젝트는 초반부터 Git으로 관리한다. 대용량 원본 아트 파일과 오디오 파일이 많아지면 Git LFS 또는 별도 백업 방식을 검토한다.

### 3.6 Steamworks

- 공식 사이트: https://partner.steamgames.com/
- Steam Direct 등록비: 게임당 $100
- 해당 게임의 조정 총매출이 $1,000에 도달하면 등록비 회수 조건을 충족할 수 있다.
- 상점 페이지, 빌드 배포, 업적, 클라우드 저장 등은 필요한 기능만 단계적으로 적용한다.

## 5. 그래픽 제작 방식

### 권장 방식: 레이어 기반 배경 + 개별 오브젝트 + 부분 애니메이션

고정 화면 게임에서 배경과 모든 오브젝트를 하나의 이미지로 합치면 상호작용이나 애니메이션을 적용하기 어렵다. 처음부터 역할별로 이미지를 분리해 제작한다.

| 레이어 | 제작 방식 | 예시 |
|---|---|---|
| 배경 | 하나의 일러스트 또는 여러 이미지 | 벽, 창문, 하늘 |
| 바닥 | 별도 이미지 | 바닥재, 카펫 |
| 배경 오브젝트 | 개별 이미지 | 책장, 소파 |
| 상호작용 오브젝트 | 개별 PNG 및 충돌 영역 | 서랍, 시계, 액자 |
| 캐릭터 | 별도 이미지 또는 프레임 | 플레이어, NPC |
| 전경 | 별도 이미지 | 화면 앞쪽의 식물, 가구 |
| 이펙트 | Godot 애니메이션 또는 파티클 | 반짝임, 먼지 |
| UI | Godot Control 노드 | 대화창, 인벤토리 |

### 제작 원칙

1. 배경과 상호작용 오브젝트를 분리한다.
2. 상호작용 오브젝트는 투명 배경 이미지로 제작한다.
3. 원본 일러스트와 게임용 리소스를 구분해 보관한다.
4. 이미지 원본은 충분한 해상도로 보관하고 게임 출력 해상도에 맞춰 내보낸다.
5. 캐릭터나 오브젝트의 상태가 바뀌는 경우 필요한 상태별 이미지 또는 애니메이션을 준비한다.
6. 화면 크기와 비율을 초기에 확정하고 모든 스테이지에 일관되게 적용한다.

## 6. 실제 개발 아키텍처

### 6.1 기본 디렉터리 구조

```text
game/
├── assets/
│   ├── characters/
│   ├── backgrounds/
│   ├── objects/
│   ├── effects/
│   ├── ui/
│   ├── audio/
│   └── fonts/
│
├── scenes/
│   ├── main/
│   │   └── main.tscn
│   ├── stages/
│   │   ├── stage_001/
│   │   │   └── stage_001.tscn
│   │   └── stage_002/
│   ├── characters/
│   ├── objects/
│   └── ui/
│
├── scripts/
│   ├── autoload/
│   │   ├── game_manager.gd
│   │   ├── stage_manager.gd
│   │   ├── save_manager.gd
│   │   └── audio_manager.gd
│   │
│   ├── systems/
│   │   ├── interaction_system.gd
│   │   ├── inventory_system.gd
│   │   └── dialogue_system.gd
│   │
│   └── components/
│       ├── interactable.gd
│       └── inspectable.gd
│
├── resources/
│   ├── stages/
│   ├── items/
│   └── dialogues/
│
└── project.godot
```

필요하지 않은 시스템은 처음부터 만들지 않는다. 실제 게임 장르와 요구사항이 확정된 후 인벤토리, 대화, 퀘스트 등의 기능을 추가한다.

### 6.2 핵심 시스템

| 시스템 | 책임 |
|---|---|
| GameManager | 게임 전체 상태 및 진행 관리 |
| StageManager | 스테이지 진입, 종료 및 전환 |
| SaveManager | 저장 및 불러오기 |
| AudioManager | BGM 및 효과음 재생 |
| InteractionSystem | 클릭, 조사, 상호작용 처리 |
| InventorySystem | 아이템 보유 및 사용 |
| DialogueSystem | 대화 및 텍스트 출력 |

시스템 간 의존성을 최소화하고, 가능하면 Signal을 통해 이벤트를 전달한다.

### 6.3 스테이지 Scene 구조 예시

```text
Stage001 (Node2D)
├── Background (Sprite2D)
├── BackgroundObjects (Node2D)
├── Interactables (Node2D)
│   ├── Drawer (Area2D)
│   ├── Clock (Area2D)
│   └── Picture (Area2D)
├── Characters (Node2D)
├── Foreground (Node2D)
├── Effects (Node2D)
└── UI (CanvasLayer)
```

각 스테이지는 독립된 Scene으로 제작하고, 반복되는 오브젝트는 별도 Scene으로 만들어 재사용한다.

예를 들어 서랍 오브젝트는 다음 요소를 포함할 수 있다.

- 표시용 Sprite2D
- 클릭 영역인 Area2D
- 충돌 형태인 CollisionShape2D
- 상호작용 상태
- 애니메이션
- 상호작용 이벤트

### 6.4 데이터 중심 설계

스테이지별 동작을 코드에 하드코딩하지 않고 Godot Resource로 분리한다.

스테이지 데이터 예시:

- 스테이지 ID
- 배경 이미지
- 등장 오브젝트 목록
- 오브젝트 위치 및 초기 상태
- 상호작용 조건
- 획득 가능한 아이템
- 다음 스테이지 ID

이 구조를 사용하면 스테이지 수가 증가해도 공통 로직을 재사용할 수 있다.

## 8. 라이선스 및 상업적 이용 체크리스트

게임 출시 전 각 도구와 에셋의 라이선스를 확인한다.

- [ ] Godot 엔진의 MIT 라이선스 고지 포함
- [ ] 사용한 폰트의 상업적 이용 가능 여부 확인
- [ ] 구매하거나 다운로드한 그래픽 에셋의 게임 내 배포 허용 여부 확인
- [ ] 사운드 및 음악의 상업적 이용, 게임 내 배포 허용 여부 확인
- [ ] 외주 제작물의 저작재산권 및 이용 범위 계약
- [ ] AI 생성 리소스 사용 시 서비스 약관 및 상업적 이용 조건 확인
- [ ] Steam Direct 등록 및 세금·정산 정보 준비

도구 자체가 무료라는 사실만으로 해당 도구에서 가져온 모든 에셋까지 상업적으로 자유롭게 사용할 수 있는 것은 아니다. 개별 에셋의 라이선스를 별도로 확인한다.

### 최종 개발 방향

- 엔진과 기본 제작 도구에는 비용을 최소화한다.
- 게임의 차별점인 아트와 콘텐츠 제작에 예산을 집중한다.
- 스테이지 단위 Scene 구조를 사용한다.
- 배경 이미지와 상호작용 오브젝트를 분리한다.
- 공통 시스템은 재사용 가능한 Scene, Resource, Signal 중심으로 설계한다.
- 첫 번째 목표는 실제 출시 구조를 반영한 완성도 높은 테스트 스테이지 하나를 만드는 것이다.

**최종 결론: Godot 4.x + GDScript + Krita를 기본 개발 환경으로 채택한다.**
